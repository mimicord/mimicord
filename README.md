# Mimicord

Discord サーバーに常駐し、コミュニティの一員のように自然に振る舞う自律型 LLM エージェント。コマンドで呼び出す assistant 型の bot ではなく、自分の興味で話題を拾い、考え、会話に参加する「peer 型」の bot を目指すプロジェクト。

> [!NOTE]
> Mimicord は Discord の公式 Bot API 上で動作する、BOT タグ付きの通常の bot です。人間への成りすましは目的としておらず、「bot だとわかった上で、どこまで自然にコミュニティに溶け込めるか」を探求します。

## 概要

多くのコミュニティサーバーは、ほとんどの時間が静かです。Mimicord は、その場に自然な存在感を持って参加する bot です。質問に答えるだけの assistant ではなく、ニュースや話題を自分の興味で拾い、意見や疑問を口にし、他のメンバーの発言に適度に反応する――そんな「生きた参加者」の振る舞いをモデリングします。

LLM を「道具」として使うアプローチは数多くありますが、「自然な会話参加者としての振る舞い」を本格的にモデリングする試みはまだ少なく、Mimicord はそこに取り組みます。

このリポジトリは、その探求の成果物となる OSS サーバー実装です（現在は設計フェーズで、実装はこれから。「ステータス」参照）。直近の目標は作者自身のサーバーでの公開・運用ですが、最終的には作者がホストする公開サービスとして提供することを目指しており、このリポジトリはその Server 部分の upstream であり続けます — Misskey.io に対する Misskey のような関係です。

当面は作者自身の日本語小規模サーバー 1 つに最適化して運用・調整します。短文の burst・ノリ・絵文字 / リアクションといった日本語 Discord の会話文化を一次対象とし、汎用化は振る舞いモデリングが成立してから取り組みます。

## 提供するもの / しないもの

**提供するもの:**

- peer 型 bot の OSS サーバー実装（Go gateway + stateless LLM worker）。将来の公開サービスの upstream（実装はこれから。現時点の提供物は設計ドキュメントが中心）
- 設計ドキュメントと運用知見（発話抑制・presence・キャリブレーションの実験結果）
- （将来）作者がホストする公開サービス — 招待して使えるホスト版。直近のスコープ外だが、これが最終目標

**しないもの（non-goals）:**

- インフラ非依存な self-host の第一級サポート。OSS として動かすのは自由だが、GCP 等のクラウドサービスへの依存は許容する
- 汎用フレームワーク・ライブラリとしての提供。汎用化は振る舞いモデリングが成立してから検討する
- assistant 的な機能（コマンド応答・便利機能）の充実
- 人間への成りすまし（後述の透明性方針を参照）

このリポジトリには汎用実装とサンプル設定のみを含めます。作者インスタンス固有の人格 config・デプロイ設定・シークレット・予算などの運用パラメータは private リポジトリ（`mimicord/deploy`）で管理します（Misskey 本体とインスタンス運用の分離と同じ構図）。

## 設計原則

- **「いつ喋らないか」を最重要視する。** 人間はサーバーの大半のメッセージを読み流し、反応するのはごく一部。常に気の利いたことを言う bot は不自然です。設計の主戦場は生成ではなく*抑制*にあり、発話のしきい値がそのまま性格パラメータになります。
- **engine と interface の分離。** 自律的な活動（調べる・考える・作る）が *engine*、自然な振る舞い（発話リズム・抑制・リアクション）が *interface*。engine が「話すネタ」と「自発的に口を開く理由」を供給し、interface がそれを自然なかたちで出力します。
- **autonomy が主、reactive が従。** 自分から動くループが本体で、話しかけられたときの応答はそのループへの*割り込み*として扱います。
- **意図的な能力の制限。** 50 のソースを 5 秒で要約し、24 時間稼働し、複数タスクを並列でこなす――これらはすべて不自然です。一度に一つのことに取り組み、現実的な時間をかけ、完成品ではなく過程を共有する方向に設計を倒します。
- **失敗と過程を共有する。** 「うまくいかなくて 1 時間溶かした、誰か知らない?」という発言は会話を生みます。成功報告だけを流す bot は距離を感じさせます。

## コアループ

```
[trigger]            news polling / サーバーの話題
   │
   ▼
[興味フィルタ]        bot の興味プロファイルに合うものだけ拾う
   │
   ▼
[engine]             Tier 1: 意見・疑問を持つ（軽量 / alpha）
   │                 Tier 2: sandbox で実際に試す（将来）
   ▼
[presence 層]        read delay → typing → 短文 burst → 可変タイミング
   │
   ▼
[共有]   ──────────▶ [memory]  いつ何を調べ・何に取り組み・何を言ったか
```

メンションや返信への応答は、このループへの **interrupt handler** として乗ります。

## アーキテクチャ

### Gateway（Go, 常駐）

`discordgo` で Discord Gateway WebSocket を保持し、全イベントを受ける常駐プロセス。軽量なルールベースの一次判定（L0）とメッセージの ingest を担当します。in-process の状態は使い捨ての判定キャッシュのみに留め、stateful にしません。

### LLM worker（stateless）

生成のたびに起動され、LLM API を呼ぶステートレスな worker。会話の文脈はリクエストで渡すか store から読み込みます。

### 段階的 gating

全メッセージを LLM に通さず、段階的に絞り込みます:

| 段階 | 実装 | 役割 |
|------|------|------|
| L0 | Go 内のルール | mention/reply の有無、直近発言からの経過時間、流速。大半をここで処理 |
| L1 | 軽量 LLM | L0 で判断が曖昧な場合のみ「発話すべきか」を判定 |
| L2 | 上位 LLM | 応答の生成 |

### 記憶 / 状態

- **hot**: Redis。チャンネルごとの直近メッセージと gating シグナル（TTL キー、sorted set の sliding window によるレート計測）。
- **durable**: Firestore（あだ名・関係性などの事実記憶、将来）。エピソード記憶とベクトル検索も将来の拡張として検討。

### presence 層

typing インジケータを「レイテンシ隠蔽 + 発話リズム」の道具として設計します。既読遅延 → typing（メッセージ長に比例）→ 送信 → 数秒後の追記、という一連のシーケンスで構成し、1 つの長文ではなく**短文の burst（2〜4 メッセージ）** に分割します。遅延予算は `max(自然な遅延, cold start + 推論時間)`。

### サーバーごとのキャリブレーション

「自然な発話リズム」の適正値はサーバーごとに異なります。グローバルな prior にライブトラフィックからのオンライン更新を重ね、各サーバーで自己調整します。生メッセージは保存せず、online estimator（EWMA, t-digest/reservoir, decaying counter）の状態のみを保持します。alpha では単一サーバーでの運用が前提ですが、この機構は将来のマルチサーバー化を見据えてサーバー単位で設計します。

## ロードマップ

### alpha（現在の目標）

「自然に会話に参加し、リアクションを返す」を、単一の日本語小規模サーバーで成立させる。

- presence 層（発話・リアクション・リズム・burst・gating）
- **Tier-1 engine**: news や話題を拾って*意見や疑問*を発話する（sandbox なし）。フィードの転送ではなく、相槌や疑問という会話の振る舞いとして。
- **人格・興味プロファイルの config 化**: 興味・口調・発話しきい値（= 性格パラメータ）を config で定義し、スラッシュコマンドで運用中に調整できるようにする。
- **安全装置**: kill switch・チャンネル allowlist・発話/コストのハードリミット（詳細は「安全と制御」）。

実装は次の順で進める予定です: ① Gateway 接続 + L0 gating → ② メンション/返信への応答（interrupt handler）→ ③ presence 層 → ④ Tier-1 engine → ⑤ 人格 config + スラッシュコマンド。安全装置（kill switch・ハードリミット）は ① の時点から組み込みます。

### beta

- **人格学習**: 会話・リアクション・メンバーからのフィードバックを通じて、興味プロファイルや発話しきい値を自己調整する。
- **記憶システムの第一歩**: Firestore の事実記憶（あだ名・関係性など）。

### 将来

- **Tier-2 engine**: sandbox 内で実際に*調べ・作り・動かして*、結果（と失敗）を報告する。
  - sandbox の隔離は到達範囲とクレデンシャルで設計。実環境の認証情報は持たせず、network egress は遮断または allowlist。
  - LLM 生成コードは untrusted として扱い、microVM（Firecracker/Kata）や gVisor 上で実行。
  - 同時進行は 1 プロジェクトに限定し、永続 workspace で「昨日の続き」という継続性を持たせる。
- **記憶システムの拡張**: エピソード記憶 → ベクトル検索。
- **マルチサーバー対応**: Gateway の sharding と Redis への状態外出しによるスケールアウト。おまけではなく、ホスト版サービス公開の前提。
- **公開サービス化**: 作者ホストのサービスとして提供する。このリポジトリはその upstream であり続ける。

## 成功基準

alpha の「成功」を次の 3 つで定義します。

1. **会話が生まれる** — bot の自発的な発話に人間が反応し、話が続くことがある。無視されないこと。bot 起点メッセージへの返信率で計測する（計測はメタデータのみで行う。「データとプライバシー」参照）。
2. **違和感がない** — サーバーの人間メンバーが「いるのが自然」「邪魔じゃない」と感じる。主観評価でよい。
3. **稼働の安定性** — 暴走・連投をしない。LLM コストが設定した予算内に収まり、無人で回り続ける。

## 技術スタック

- **Go** + [`discordgo`](https://github.com/bwmarrin/discordgo) — Gateway / イベント処理 / オーケストレーション
- **LLM API** — 軽量モデル（L1 判定）+ 上位モデル（L2 生成）のデュアル構成
- **Redis** — hot な状態・バッファ
- **Firestore** — durable な記憶（将来）
- **コンテナ（Docker）** — Gateway / LLM worker の配布形態。実行基盤は特定しない（Docker 単体・Kubernetes・VM 直置きのいずれも可）。作者インスタンスは GKE + ArgoCD（GitOps）で運用（設定は private リポジトリ側）
- **microVM / gVisor** — Tier-2 sandbox（将来）

## 透明性についての方針

Mimicord は Discord の公式 API を使う通常の bot であり、BOT タグが表示されます。user token による自動化（self-bot）は行いません。目指すのは人間への成りすましではなく、「bot だと知られた上で、コミュニティの一員として自然に振る舞えるか」という振る舞いのモデリングです。

## データとプライバシー

Mimicord はサーバーのメッセージを読んで動作しますが、データの扱いは最小限に設計します。

- **生メッセージを長期保存しない。** 会話文脈は Redis に TTL 付きで短期保持し、キャリブレーションは online estimator の状態のみを持ちます（生ログ非保存）。
- **記憶はオプトアウト可能にする。** 将来の事実記憶・エピソード記憶は、メンバー単位のオプトアウトと管理者による消去手段を前提に設計します。
- **計測はメタデータで行う。** 成功基準の計測（返信率など）はメッセージ本文を使わず、「返信があったか」というメタデータのみで行います。
- **審査に耐えるデータ設計を維持する。** Message Content Intent は bot が 100 サーバーに到達すると Discord の審査対象になります。公開サービス化の前提条件として、データの用途と保持を常に説明可能な状態に保ちます。

## 安全と制御

自律的に発話する bot は assistant 型より一段リスクが高いため、alpha の最初期から次の安全装置を組み込みます。

- **kill switch / mute**: 管理者がスラッシュコマンドで即座に発話を停止できる。
- **チャンネル allowlist / denylist**: bot が読む・発話するチャンネルを管理者が制御できる。
- **ハードリミット**: 発話レート（連投防止）と LLM コスト（月額予算）に上限を設け、超過時は自動で発話を止める。具体的な予算額は運用側の設定値とする。
- **外部入力は untrusted として扱う**: メンバーの発言や news ソースによる誘導（prompt injection）を前提に、システム指示と外部入力を分離して扱う。
